# 6502 → AArch64 JIT lab

A **teaching / verification experiment**: write a 6502 interpreter from scratch,
then add a JIT that translates 6502 basic blocks into AArch64 machine code, and
answer three questions with reproducible numbers:

1. What does the JIT turn "fetch → decode → dispatch → execute" into?
2. On a minimal instruction set like the 6502, how much faster is a JIT really —
   and when does it end up slower?
3. What does the JIT cost: code cache, self-modifying code, debuggability?

Most of the lab stands alone: the CPU, the JIT and the benchmarks do not depend
on NEMU. The NES stage pulls in this project's own PPU and mapper
(`NEMU/src/nes/`) so frames can be compared one by one. It is not part of the
main build.

## Quick start

```sh
cd labs/jit6502
make                      # builds bin/jit6502
python3 tools/make_bench.py bench

# Download the Klaus functional test (~64 KiB) to /tmp/klaus.bin
curl -fsSL -o /tmp/klaus.bin \
  https://raw.githubusercontent.com/Klaus2m5/6502_65C02_functional_tests/master/bin_files/6502_functional_test.bin

./bin/jit6502 klaus /tmp/klaus.bin --engine=interp           # interpreter baseline
./bin/jit6502 klaus /tmp/klaus.bin --engine=jit --chain     # machine-code JIT
./bin/jit6502 selfcheck 20000                                # random differential test
make test                                                    # all of the above + benchmarks
```

Common options:

| Option | Meaning |
|---|---|
| `--engine=interp\|jit` | Pick the execution engine |
| `--chain` / `--no-chain` | Enable block chaining (throughput vs exact instruction counts) |
| `--code=LO-HI` | Declare the "may be written" code window, default `0x0400-0x8000` |
| `--max-inst=N` | Instruction budget (strict when `--no-chain`) |
| `--stop-pc=ADDR` | Stop when the guest reaches this PC (blocks never cross it) |
| `--trace=FILE` | Per-instruction / per-block state (the JIT only logs block entries) |
| `--mem=ADDR:LEN` | Dump memory after the run, to check stores |
| `--stats` | Print the number of compiled blocks and invalidations |

## JIT concept → code

| Concept | Where it lives in this lab |
|---|---|
| Interpreter dispatch cost | `switch (info.op)` in `interp.c`: one fetch, one table lookup, one branch per instruction |
| Basic block | `jit_compile()` translates linearly from `start_pc`, ending on any branch/jump/call/unsupported opcode |
| Guest state in host registers | `x19=Cpu*`, `x20=mem`, `w21..w25=A/X/Y/SP/P`, `x26=mem+PC`, `x27=cycles` |
| PC as a host pointer | Lets immediate and zero-page operands be loaded with a single `ldrb wN, [x26, #disp]` |
| Code cache | `g_map[65536]`: PC → compiled function |
| Direct map vs hash | 64K array, a hit is one O(1) lookup |
| Block chaining | When the target is already compiled, `br` straight to its resume point, skipping "epilogue → dispatch → prologue" |
| Self-modifying code | A translated store that hits the code window records the page and exits the block; the dispatcher drops only that page |
| Fallback path | Untranslated instructions (BRK/RTI/JMP indirect) step through the interpreter |
| Instruction counting | Each block returns the number of instructions it actually executed (back-patched on early branch exit), so budgets and stop points stay exact |

Register convention (callee-saved inside a block; the prologue/epilogue handles
the C world):

```text
x19 Cpu*     x20 mem        w21 A       w22 X       w23 Y
w24 SP       w25 P          x26 mem+PC  x27 cycles  w28 0x7D (clears N/Z)
x29 resume table base        w0  instructions executed (accumulated across blocks)
```

## Correctness

- **Klaus functional test**: all three paths (interpreter, unchained JIT, chained
  JIT) stop at `PC=$3469` and **execute exactly the same instruction count**:
  `30,646,176`.
- **Fixed-budget state comparison**: running N instructions of the same image
  gives identical `pc/a/x/y/sp/p/cycles` for the interpreter and the JIT
  (`make test` covers N=100k/1M/5M).
- **Random differential test**: every opcode gets random registers and random
  memory; the interpreter and the JIT each execute one instruction, then state,
  cycle count **and the whole 64K memory** are compared; `selfcheck 20000` passes.

## Measured results

Machine: Apple M2, macOS 26.3, `clang -O2`. MIPS = executed 6502 instructions per
second.

| Workload | Interpreter | JIT (no chain) | JIT (chained) | Speedup |
|---|---:|---:|---:|---:|
| Klaus functional test | ≈85 | ≈145 | **≈750** | **≈8.8×** |
| `arith_loop` (ADC/STA/INX/BNE) | ≈100 | ≈41 | **≈620** | **≈6.2×** |
| `copy_loop` (indirect copy) | ≈110 | ≈39 | **≈827** | **≈7.5×** |
| `call_loop` (JSR/RTS) | ≈104 | ≈27 | **≈681** | **≈6.5×** |

Numbers move ±15% with machine load; the order of magnitude is the point, and
`make test` prints them again on every run. Klaus cache behaviour: `1697` blocks
compiled, `254` page flushes, `0` full flushes.

### Three conclusions you can reproduce

**1. Without block chaining, the JIT loses to a well-written interpreter.**
With `--no-chain` every block pays the fixed cost of "save/restore registers +
return to the dispatcher"; the benchmark loops are only 4–6 instructions per
block, which cannot amortise it.

```sh
./bin/jit6502 bench bench/arith_loop.bin --engine=jit --no-chain --code=8000-10000   # ~41 MIPS
./bin/jit6502 bench bench/arith_loop.bin --engine=jit --chain    --code=8000-10000   # ~636 MIPS
```

**2. Invalidation range matters more than "having a JIT".**
The larger the window declared by `--code`, the more data stores are mistaken for
possible code writes. Declaring Klaus's data segment as code as well (it executes
`ex_*` stubs at `$0200`) pushes flushes from 254 to 303,611 and drops throughput
back to interpreter level:

```sh
./bin/jit6502 klaus /tmp/klaus.bin --engine=jit --chain --stats                    # ~747 MIPS, 254 flushes
./bin/jit6502 klaus /tmp/klaus.bin --engine=jit --chain --code=200-3800 --stats    #  ~87 MIPS, 303k flushes
```

**3. A full flush is not automatically a disaster — it depends on how many code
writes actually happen.** Forcing a whole-table flush with `JIT_FULL_FLUSH=1` on
the same Klaus image still gives ~747 MIPS, because only 254 writes land on code
pages. The real problem is treating data pages as code pages.

## NES integration: running real games through the JIT

The `nes/` directory wraps the lab CPU in a NES machine, in three steps:

1. **NES core** (`nes/ppu.c`, `nes/apu.c`, `nes/cart.c` come from this project's
   NEMU; `nes/nes_system.c` is the bus/controller/PPU/APU glue): get the
   interpreter running first. Verification is frame-by-frame against NEMU — same
   60 frames, same ROM, both screenshots **SHA-256 identical**, same cycle count.
2. **JIT bus mode** (`jit_set_bus_mode`):
   - `$0000-$1FFF` takes the fast path (direct 2 KiB WRAM access, address `& 0x7FF`);
   - `$2000+` calls the bus helper (PPU registers, mapper, controller);
   - the helper first advances the PPU to the current CPU cycle (`nes_sync`) and
     then reads or writes the register, so polling `BIT $2002` for vblank behaves
     exactly like the interpreter;
   - chaining is kept, but checks `JitRuntime::pending` before linking: on a frame
     boundary or a pending interrupt it returns to the dispatcher, and NMIs are
     sampled at instruction boundaries;
   - self-modifying-code detection is off in NES mode (code lives in ROM).
3. **SDL window + audio** (`nes/frontend_sdl.c`): `--window` opens a playable
   window with the same key mapping as NEMU (WASD/arrows, Space/Z, X, C, V, Esc).
   The APU is mapped at `$4000-$4017` (including the frame IRQ) and SDL plays a
   44.1 kHz mono queue; `--wav=FILE` exports the same audio for verification.

```sh
# Headless comparison (one command, switch engines)
./bin/jit6502 nes ../../roms/falling.nes --frames=60 --screenshot=/tmp/i.ppm --engine=interp
./bin/jit6502 nes ../../roms/falling.nes --frames=60 --screenshot=/tmp/j.ppm --engine=jit
cmp /tmp/i.ppm /tmp/j.ppm        # must be identical

# Play through the JIT (with sound)
./bin/jit6502 nes ../../roms/falling.nes --engine=jit --window --scale=3

# Export audio for inspection
./bin/jit6502 nes ../../roms/falling.nes --frames=300 --wav=/tmp/game.wav --engine=jit
```

Measured (`falling.nes`, 600 frames = 10 s of game time, Apple M2, `clang -O2`,
default `--no-chain`):

| Engine | 600 frames | Throughput | Notes |
|---|---:|---:|---|
| Interpreter | ≈0.64 s | ≈940 fps | |
| JIT | ≈0.44 s | ≈1380 fps | 131 blocks, 599 interpreter fallbacks, 0 flushes |

The NES speedup (≈1.5×) is far smaller than on pure CPU workloads (6–9×), for a
simple reason: every frame is full of `$2002` polling and PPU register accesses,
each of which goes through a helper and syncs the PPU, and blocks are cut very
fine by I/O and branches (the loop at `$C0CA` is only ~3 instructions per block;
600 frames dispatch 5.6M blocks). That is the on-site evidence that "a JIT is not
a silver bullet" — but once the external costs in the next section were pushed
down, the JIT finally went from "slower than the interpreter" to "1.5× faster".

## NES performance work: measure first

The first measurement of `falling.nes` 600 frames was **JIT ≈1.37 s, interpreter
≈1.14 s**: the JIT was losing. A `sample` profile explained it — **78% of the time
was not in the JIT at all but in `ppu_step()`, called once per block from
`nes_sync()`**:

```text
jit_run 92%
  nes_sync 84%
    ppu_step 78%      <- 61,440 visible dots per frame, each re-fetching tile/attribute/pattern
```

The PPU re-fetched the tile on every dot: 61k dots per frame, each doing four
indirect calls (`nt_index` ×2, `chr_read` ×2) — the same data the hardware fetches
once per 8 dots. So the work went in this order: remove external overhead first,
then change the hot loop. Every step was validated by **byte-identical frames**
across 6 ROMs:

| Change | What it does |
|---|---|
| Cache `getenv` | The dispatcher read `JIT_CHAIN_BUDGET` on every block — 5.6M reads per 600 frames; now read once at init |
| PPU tile cache | The same tile is reused for 8 consecutive dots; the cache is dropped when `v` moves (dots 256/257, new scanline) |
| Direct CHR indexing | Mapper 0 does not bank CHR, so pattern reads index `cart->chr[]` directly, dropping the indirect call and the modulo |
| Batched scanline drawing | Visible dots no longer test for events one by one; runs are drawn in batches, and the event dots (0/1/256/257/339) are handled explicitly |

The whole-line pre-fill in `prepare_scanline()` went away too: dots 1..256 already
write all 256 pixels, so the pre-fill simply did the same work twice.

Result (same machine, same ROM, same command, alternating runs, best of N):

| | Before | After | Gain |
|---|---:|---:|---:|
| Interpreter | 1.14 s | 0.64 s | 1.8× |
| JIT | 1.37 s | 0.44 s | 3.2× |
| JIT / interpreter | 0.83× (slower) | 1.47× | — |

The two curves do not improve by the same factor: PPU cost is identical for both
engines, so the gain in "JIT relative to interpreter" comes from the JIT-side
`getenv` removal and fewer dispatches, while the absolute frame rate gain is
mostly the PPU.

Correctness gate (`make test` green):

```text
Klaus            all three paths PASS, identical instruction counts
State compare    identical at 100k / 1M / 5M instructions
Random diff      20,000 instructions, state + cycles + all 64K memory
NES              falling.nes frame 60 SHA-256 matches the NEMU reference, same audio sample count
GEM6502 DiffTest per-instruction trace and checkpoints agree (PPU scanline/dot included)
```

Frame-level regression uses 6 ROMs (`falling`, `hanoi`, `file-fixers`,
`galaxypatrol`, `stallar`, `table_tennis`): the interpreter and the JIT produce
identical 200-frame screenshots — any timing slip in the PPU shows up immediately.

## DiffTest: GEM6502 as the reference model

`scripts/difftest_gem6502.sh` runs JIT6502 in lockstep with the repository's
GEM6502 fast model:

| Layer | Method | Covers |
|---|---|---|
| Instruction trace | Both sides emit the same 16 fields via `--trace-state` (pc/a/x/y/sp/p, six zero-page cells, cycles, PPU scanline/dot, NMI) | JIT single-instruction block semantics, PPU/APU sync, cycles |
| Instruction checkpoints | Both sides align on **step count** at N instructions and compare final state | Multi-instruction blocks (JIT runs with `--no-chain` so the budget is exact) |
| Frame-level runs | Same frame count, compare PC | Stability in chained mode |

```sh
make difftest                  # falling.nes, 200,000 steps by default
./scripts/difftest_gem6502.sh ../../roms/falling.nes 500000 120
```

This comparison caught three real bugs during development:

1. **OAM DMA's 513 cycles were dropped by the JIT**: the bus helper wrote
   `Cpu.cycles` directly, and the block epilogue then overwrote it from `x27`.
   Fixed by recording `extra_cycles` and absorbing it in the sync hook.
2. **`--no-chain` was overridden in NES mode**: `cmd_nes` turned chaining on
   unconditionally, so chained execution ran past the budget and checkpoints
   misaligned.
3. **Alignment semantics**: GEM6502's `instructions` counter excludes DMA stall
   steps, so `--max-inst` walked 18 steps further; both sides now use
   `--max-steps` / step alignment, after which they agree bit for bit.

### Known approximations in NES mode

- Only the CPU side of mappers 0/1/2/3/4/7 is implemented. The APU is wired up,
  but sample boundaries are not sample-exact against NEMU: over 300 frames this
  lab produces 220,135 samples and NEMU 220,134, with a waveform correlation of
  about 0.67 (the APU steps at "block + I/O access" granularity, not per
  instruction).
- Indexed and indirect memory accesses do not split blocks, so the PPU can lag by
  up to one block; common games do not notice, but cycle-exact test ROMs may
  disagree.
- No save states, replay or recording; the window is fixed at 3× scale.
- **Chaining is off by default in NES mode**: with chaining the PPU only advances
  on I/O accesses, so long pure-RAM sequences delay the vblank NMI and shift
  in-frame register writes, which shows up as horizontal black stripes. Unchained,
  600 frames now take ≈0.44 s (≈1380 fps), well past 60 fps gameplay. `--chain`
  remains an explicit experiment option (more throughput, but the picture may
  tear).

## Known limitations

- Official NMOS 6502 opcodes only; interrupts (NMI/IRQ) are sampled at instruction
  boundaries in NES mode, and pure CPU mode has no interrupt sources.
- The flat 64 KiB mode is still a pure CPU experiment (Klaus/benchmarks); only NES
  mode has the PPU/APU/bus.
- Blocks never cross a 256-byte page (so page invalidation holds), and are capped
  at 48 instructions.
- No register allocator or constant pool: registers are a fixed mapping, and
  helper addresses are materialised with `movz/movk`.
- `--code` must cover every region that can be written; code that is only executed
  and never written may live outside the window.
- Chained mode relaxes `--max-inst` strictness for throughput (chained execution
  can slightly overshoot the budget); use `--no-chain` when counts must be exact.

## How this relates to the rest of the project

The conclusions of this lab are separate from the repository's main line:

- **The NEMU / RTL verification chain does not need a JIT.** The RTL side is
  orders of magnitude slower, so the reference model is not the bottleneck, and
  DiffTest wants per-instruction, per-cycle reproducibility — a JIT only adds
  mismatch surface.
- **The browser player does not need a JIT**: wasm cannot generate code at runtime,
  and the browser is already JIT-compiling wasm.
- The cases that genuinely justify a JIT are "large-scale regression / fuzzing /
  low-end devices", and the cheap optimisations come first — caching `getenv`,
  cutting per-instruction dispatch, batching PPU work per scanline. All three are
  already in place here (see "NES performance work" above), and they paid off more
  than tuning the JIT itself.

## Next steps

1. **I/O fast path**: inline `$2002`/`$2007` to cut helper and PPU-sync overhead
   (NES is at ≈1.5×; this is still the biggest remaining cost: 5.6M dispatches and
   9.4k `nes_sync` calls per frame).
2. **Chaining plus a cycle watchdog**: `--chain` is faster but currently runs past
   vblank, so frames do not match. Checking "more than N cycles since the last
   sync → return to the dispatcher" at the resume point would give both chaining
   and correct timing.
3. **Sample-exact audio**: align the APU step boundaries with NEMU and raise the
   waveform correlation above 0.67.
4. Give blocks a register allocator; replace "write ⇒ invalidate" with a page table
   plus write protection.
5. Instruction-level trace comparison (the JIT can only compare at budget level
   today).
